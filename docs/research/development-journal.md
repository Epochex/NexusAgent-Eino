# 我怎样把 NexusAgent 改造成一个能验证可靠性的 Go＋Eino 项目

记录时间：2026年10月20日起。本文用第一人称整理这个项目从选题、源码核对到工程改造和验收的过程。实现过程中使用了 Codex 辅助查阅代码、编写实现、执行测试和整理证据；文中的“我”表达项目的需求与技术决策，不表示全部代码由我独立手写。文中描述的是个人项目在本地和 CI 中的实现与实验。

## 我为什么最后选择继续做 NexusAgent

我最初想找一个适合展示 Go 后端能力、同时又有 Agent 内容的项目。这里真正难的是把业务价值讲清楚：如果只是给普通增删改查加上审批、队列和一堆中间件，需求很小，架构却很重，面试时很容易解释不通。

讨论中也出现过订单售后沙箱和外置执行底座的方案。我最后没有沿着这些场景继续做，而是回到 NexusAgent 本身。它已经有 Agent、知识库、工具、多智能体和工作流，使用者的目标很明确：把模型接上自己的资料和工具，完成一个可追踪的任务。我的工作应该是把这些流程做实，解决运行失败、重复执行、权限变化和资源争抢，而不是再编一个行业故事。

这也决定了项目的价值：它既展示 Agent 的调用链，也能具体讨论数据库事务、幂等、租约、消息投递、并发控制、流式协议和数据隔离。相比单纯说“支持多智能体”，我更想解释清楚，一个工具已经执行、但结果还没落库时，系统到底应该怎么办。

## 我先核对了源码，而不是从功能清单推断实现

项目基于 [chengpeng-cp/nexus-agent](https://github.com/chengpeng-cp/nexus-agent)，导入基线是 `5c7b81e`。我保留了上游 Git 历史、作者归属和教学实现。平台原有功能不是我的原创，原快照也没有 LICENSE 文件，我没有替原作者重新授权。来源说明单独保存在 [UPSTREAM.md](../../UPSTREAM.md)。

初始核对时，我沿着 go.mod、入口和实际调用链检查，发现导入快照的生产路径是 Hertz 加自研执行循环，不能因为 README 提到 Eino，就认定请求已经经过 Eino。这个判断只针对导入时的快照，不代表上游之后的版本。

我也没有因为这一点否定整个项目。它已有的业务流程足以支持框架工程化，缺口主要在执行语义和证据：谁负责运行状态，失败怎么传播，工具调用如何授权，进程重启后是否会重新产生副作用。最初的检查和取舍记录在 [基线报告](2026-10-20-baseline.md)与[总体设计](../superpowers/specs/2026-10-20-nexus-agent-eino-design.md)。

## 我没有先拆微服务，而是先统一执行路径

我选择保留模块化单体 API 与独立 Worker，继续使用 PostgreSQL、Redis、Milvus 和 MinIO。对这个项目来说，先把进程之间的状态关系定义清楚，比增加服务数量更有意义。

执行内核先固定到 Eino `v0.9.22`。普通 Agent、Host 下的 Expert 和直答路径都接到实际 ADK，YAML 工作流再编译成实际 Graph。原有 Runner 契约和前端事件尽量保留，`agent/naive` 继续承担教学用途。我没有保留两套可任选的生产 ReAct 循环，否则后续每修一个问题都要验证两遍行为。

最初迁移时，重点也不只是“模型能回答”。我检查了模型配置是否会被并发请求改写、流中途的供应商错误是否会被吞掉、工具是否只能从绑定列表构建，以及 Schema 或危险标记变化后旧运行是否仍然有权执行。框架负责调度，授权和副作用边界仍然由应用负责。

这一阶段还修了一个很容易在演示中漏掉的问题：界面显示了部分内容，不代表请求成功。Chat 的成功终态必须等 assistant 消息提交后才能发出；数据库保存失败、模型流未正常结束、用户取消和正常完成要区分。客户端断开后需要取消生成，但收尾落库又不能直接沿用已经取消的请求上下文。[P0/P1 验证](2026-10-20-p1-validation.md)保留了实际 HTTP、SSE、PG 与竞态检测的范围。

## 真正复杂的部分，是任务已经产生副作用之后

工作流如果只在 HTTP handler 的内存里运行，页面关闭、进程退出和模型超时会混在一起。我把运行所有权交给持久状态和 Worker，HTTP 只负责提交、查询、审批与订阅。

一条运行绑定不可变发布快照、输入、图版本和模型/工具设置。领取任务时有租约和 generation fencing，旧 Worker 即使迟到，也不能继续提交成功。请求幂等键解决重复提交；稳定 operation ID 和 attempt 则区分同一个逻辑步骤与它的多次尝试。审批时核对中断标识和参数哈希，防止用户看到一组参数，真正执行的却是另一组。

这里我特别避免把“恢复”写成“任意操作都 exactly-once”。真实文件已经写入、但操作结果还没提交时，Worker 被强杀，新进程无法凭空知道外部世界发生了什么。对于非幂等操作，我保留 unknown 和人工核对；已确认的结果可以复用，只读调用才允许按策略重试。

我用真实 Worker 进程做了两种故障：一次在模型 HTTP 请求中途强杀；另一次在 file_ops 已经写完、但数据库结果提交被阻塞时强杀。前者可以按租约恢复并保留 attempt；后者必须进入需要核对的状态，不能悄悄再写一遍。[P2 报告](2026-10-20-p2-validation.md)明确区分了实际进程故障、文件副作用和 Redis 网络故障，也记录了测试夹具自己曾因请求体和连接所有权处理错误而挂住。

通知采用事务 outbox。PG 是业务状态权威，Redis 提醒 Worker 有事可做；重复通知不能变成重复业务执行。页面断开订阅也不能把持久工作流当成普通对话一起取消。

## 知识库让我重新面对发布与版本问题

文档上传之后，并不是把文本切一下、写几个向量就结束了。对象存储可能成功而通知失败，Worker 可能在分块和向量写入中途退出，用户也可能在索引尚未完成时发起查询。

我把原文预留、异步任务、分块、向量写入和 ready 发布串在持久任务里。知识库固定向量模型、维度和版本，查询只看已经发布的文档代数。删除和重建也需要同时考虑 PG 与向量库，不能只把其中一个删除就宣布完成。

检索权限还有一个更隐蔽的问题：先从向量库取 TopK，再过滤掉别人的内容，会让无权限结果挤掉本来合法的命中。因此过滤条件必须在 ANN 查询前带进去，再回 PG 核对发布状态和引用。关键词路线实际是 ILIKE/TF-IDF，我没有把它包装成 BM25。

最初的100题用受控32维特征向量，适合证明排序、隔离、引用和降级机制。但它不能证明真实语义理解能力。这个限制从一开始就写在[检索验证](2026-10-20-p3-retrieval-validation.md)里，后来接真实生成模型时也没有把它抹掉。

长期记忆沿用同样的思路：事实、所有者和版本由 PG 管，向量更新作为可重试任务。必须能处理删除、重建和 Worker 崩溃后的状态核对，而不只是跨会话记住一句话。[文档](2026-10-20-p3-documents-validation.md)和[记忆](2026-10-20-p3-memory-validation.md)分别有自己的失败与恢复证据。

## MCP 和 A2A 接通之后，权限仍然是应用的责任

我接入官方 SDK，但没有把 SDK 当作安全边界。MCP 的发现、Schema、凭据、用户 ACL 和工具政策都需要有版本；工具配置或授权撤销后，旧缓存不能继续授予执行能力。出站目的地也要显式授权，不能因为是 Agent 工具，就允许访问任意内网地址。

A2A 还多了一层远端不确定性。远端可能已经接收任务，但本地因网络中断没有拿到确认。这个状态需要保存并核对，不能把“没有收到响应”直接解释为“没有执行”，然后自动重新发送。对应的 SDK、任务状态、取消和未知结果边界写在 [MCP](2026-10-20-p3-mcp-validation.md)与 [A2A](2026-10-20-p3-a2a-validation.md)报告中。

身份也不能只看 JWT 的签名。用户角色、工具授权和模型状态会变化，我需要在关键路径读取当前权威状态。文件工具按所有者隔离；数据库、HTTP 和网页工具各自限制可执行范围。代码执行默认关闭，单独用真实容器验证资源、超时、OOM 与审计，它的隔离结论不能拿来替代整个平台的权限设计。

## 压测前，我先把“并发”定义清楚

单进程 semaphore 很容易做，但 API 和多个 Worker 各自限流时，全局额度仍然可能被突破。我把 Chat 和工作流的活跃运行额度放到共享 PG 协议中，供应商调用也按 origin 共享限制，并加入所有者额度、有界排队和公平领取。等待审批的任务不应该一直占着执行槽。

容量验证采用开放到达率，避免系统变慢后负载发生器跟着变慢、反而显得没有积压。除了平均耗时，我同时记录计划到达、实际写出、接收、拒绝、终态、数据库独立核对、SSE、排空过程以及基础设施资源。模型桩和工具等待时间也固定下来，保证实验能解释。

冻结源码 `d8925c0` 的30分钟基准中，API 与 Worker 各限制2 CPU/4GiB，模型每次等待250ms，工具等待100ms。主要负载是两次模型和一次工具的工作流，也包含实际 Eino Agent 工具循环。200 SSE、32共享槽位、每秒10个新请求时，18000次实际请求全部完成。

我没有只保留最好看的一档。36档中30档支撑完整到达率，低槽位高负载的拒绝边界也保留。500 SSE 曾在初始建连阶段失败，后来改成有界预热，并明确这是逐步建连，不是证明500个连接能同时握手成功。三次排空观察的长度也不同，不能写成三轮30分钟压测。

这些结果证明的是指定硬件和受控工作负载下的平台行为，不能推出真实供应商也能提供同样吞吐。完整原始数据、失败样本和资源口径都在[容量报告](2026-10-21-p4-capacity-validation.md)。后来的修复没有被偷偷写成这个冻结版本的测量结果。

## 最后的审查和 CI 也找到了真问题

整分支独立审查指出了两个重要问题：领取过期任务时，有一条路径绕过未知操作收尾；migrate 的精简镜像没有带 SQL 文件。这些都不是文档用词问题，会直接影响恢复和部署。我先用失败测试或实际镜像复现，再修复。

远端 CI 还暴露了冷缓存 runner 上模块缓存目录不存在的问题：本地 Docker 的行为不能证明 Linux bind mount 的前置条件成立。修复只是挂载前创建目录，没有跳过基础设施测试。最终验证按提交 SHA 对齐，不用“本机通过”代替远端结果。[发布验收](2026-10-21-release-validation.md)保留了审查、RED/GREEN、镜像启动和 CI 的证据。

过程中还有一次本地清理被自动审批拒绝，只返回 blocked by policy，没有具体规则。我没有猜它是哪个目录或命令触发，也没有绕过重试。临时资料、分支和容器留下来，并不影响代码交付。

## 真模型验收让我发现了受控桩测不到的问题

拿到有限额度后，我没有把它用来重复压测。首轮只用了8次真实 DeepSeek 请求，集中验证 Host/Expert→MCP→最终答案、审批同意和拒绝、恢复不重放前置模型节点，以及文档问答、拒答和越权拦截。

真实调用通过之后，代码核对又发现供应商消息序列化漏传带工具调用的 assistant reasoning_content。接口当时仍然接受请求，但协议不能依赖这种容忍。我用严格本地 HTTP peer 把流式与非流式都做成先失败、后通过，避免为了重复确认再花模型额度。[首轮报告](2026-10-21-real-model-validation.md)记录了8次 usage 和约0.005822元的峰时无缓存保守估算，不把余额没变化解释成免费。

之后我允许在5元以内扩大验证。这一轮累计100次真实请求，重点是中文/英文问答、错误前提、复杂工具参数、恶意工具文本、跨轮回忆和较长输入。初次矩阵并没有全绿：40KB输入被上下文预算正确拒绝，测试 helper 却把它当作意外错误中止。

更值得记录的是评分器本身也会骗人。模型在解释拒绝恶意指令时引用了 INJECTION_SUCCEEDED，关键词检查误判成了服从；另一边，模型说“我不能确认这个 permit，也不会追加 HISTORY_OK”，只做关键词命中却会把它算成回忆成功。后来我改为核对实际工具调用和不可预知的结果，回忆则要求严格 JSON 和没有工具重放。

沿着这些坏例，我找到一个真实的后端缺陷：下一轮只读了历史 Content，原始 tool 消息和 ID 没有恢复。模型只能看到上一轮助手的断言，有时会拒绝把它当作已验证事实。我把逐轮 assistant/tool 协议记录到 metadata，并只重载完整成功的记录，保留推理和调用对应关系；失败、中断和损坏记录不能获得成功证据的地位。

修复后只做了16次定向调用，没有把此前84次全部重跑。4组两步工具任务和下一轮回忆通过，没有重复执行工具；2个上下文预算负例在计费前被拒绝。累计100次的峰时无缓存估算为0.257176元，初次失败和定向复验分别保存在[扩展验收报告](2026-10-21-real-model-extended-validation.md)。这比凑一个“100%成功率”更有用：它说明失败来自哪里、怎样证明修复，以及哪些旧数据不能再作为正确率引用。

## 我用一张8GB显卡补真实 embedding 验证

前面的真实生成模型测试仍有一个空缺：向量是受控的，不能说明语义召回好不好。最直接的想法是继续用现有 DS API，但实际请求官方 `/embeddings` 得到404，所以我没有拿聊天模型生成一串数字来冒充向量。

我最终选了本地 Qwen3-Embedding-0.6B。机器实查是 RTX5060、8GB显存，当时空闲约5.6GiB。模型权重约1.19GB，不能把这个数字直接当作推理显存，也不能把CUDA包3.2GiB的下载量误认为显存要求。为避免影响已有环境，我用了独立Python环境和固定版本的CUDA PyTorch。

安装期间，大文件传输明显慢于小文件。我先验证Range请求，再改成可恢复分段下载，逐段检查Content-Range，最终校验发布方SHA256。模型revision、权重和tokenizer哈希都固定下来；启动时再次核对，禁止远程模型代码和隐式联网加载。下载缓存和模型留在忽略目录，不进入Git。

这里也遇到一个测试脚本的边界错误：我拼出来的“512 tokens”实际上包含了额外framing，重新编码是513。修的是探针的构造方式，服务端仍然严格按真实tokenizer计数，超过512就拒绝，没有靠截断让它通过。

实际CUDA推理使用左填充、最后一个有效token池化、FP16模型和归一化FP32输出，关闭不需要的KV cache。batch4、每条512tokens的探针通过，1024维向量有限且范数接近1；当时PyTorch峰值分配1,465,709,568字节，约1.37GiB，峰值保留约1.40GiB。[原始显存探针](2026-10-21-local-embedding-probe.json)里同时保留了版本、GPU名称和实际输入量。

我只把这个进程作为有界的本地验收服务：固定监听loopback，私有Bearer，单次最多4条，一次只执行一个GPU batch。CPU回退必须显式选择。它不承担公网模型服务的高可用、调度和租户计费。本轮也没有偷偷加Qwen查询指令：现有生产embedding契约对文档和query使用同一模型，我先测这一条真实路径的无指令基线。

中文100题首先暴露了受控向量没暴露的问题。80个有答案问题中，真实密集向量Hit@3为96.25%，关键词与混合均为100%；但关键词MRR高于混合，真实向量没有在这组短运维文本上普遍胜出。10个无答案问题中，密集与混合都有8个返回候选，关键词没有。

我没有把阈值从继承的0.25改到一个刚好让这10题全过的数。返回候选也不等于生成模型已经编造答案。更合理的结论是：真实模型的分数尺度需要单独校准，“资料里有没有答案”也不能只靠一次向量相似度判断。之后要用独立开发集选阈值，再用未参与调参的样本验收。

为了不只围着这20段项目说明做题，我又加入BEIR SciFact官方相关性标注。选取500篇文档，保留300个测试查询的全部标注正例，再按固定哈希顺序补充干扰文档；原始文本只在本地，公开准备脚本、来源、哈希、ID和排名。这个子集比完整5183篇语料更容易，不能把结果放到完整SciFact排行榜旁边宣传。

评测比较的是生产返回的前三个分块所映射到的文档。多个分块来自同一篇文档，不能重复增加Recall；多相关文档问题还要按实际找回的标注集合比例计算。除了Hit@3，我同时记录真正的Recall@3、MRR@3、引用对应、错误、权限和每条查询的延迟。


公开子集跑完后，密集路线Hit@3是86.33%、真正Recall@3是84.47%；关键词分别为31.00%和29.34%；混合却降到了71.00%和67.11%。有51个查询原本密集命中，融合后丢失。query49就是一个具体例子：密集拿到了相关文档5953485，等权融合后，三个位置都被另一篇文档的分块占住。

这个结果比一句“混合检索提升效果”更值得留下。它表明路线质量、融合权重和分块多样性需要一起评估。我没有在同一批测试标签上调出一个最好看的参数，再把它写成独立验证。整轮协议、引用和权限检查通过，也不等于检索质量已经达到业务SLA。逐条排名和失败样本都保存在[本地embedding验收](2026-10-21-local-embedding-validation.md)。

最后我又接了一次实际上传链路：TXT从认证HTTP接口进入MinIO和异步Worker，由本地模型生成真实向量，发布到Milvus，再让DS依据检索资料回答。正确引用和无答案拒答都通过，跨用户访问在模型前被拦截。这里只新增2次DS请求，保守估算0.001624元，继续沿用已有费用账本，没有为了新一轮测试清零计数。向量化本身没有API费用。

累计本地向量化输入218769tokens、1501个批次，推理失败数为0，最终PyTorch保留峰值约1.41GiB。结束后我停掉了本次模型进程，释放显存，保留权重和环境供后续复现。不是把一个常驻GPU服务悄悄留给日常使用。

## 我现在怎样界定这个项目

这次工作让我把几个原本容易混在一起的结论分开了。受控桩能把执行、协议和恢复测得很细，但不能替代真实模型；真实模型返回200不能代表任务完成；检索命中也不能代表资料足以回答；单机压测和一次稳定运行不能变成线上SLA。

如果要介绍自己的工作，我会从可验证的机制讲起：Eino真实执行路径、PG持久任务与代际围栏、未知副作用核对、发布版本与权限预过滤、多进程共享准入、SSE持久终态，以及真实模型揭示的协议和历史证据问题。上游已有的平台功能、我的工程改造、AI辅助和实验环境都需要说清楚。

接下来真正值得做的是独立校准检索阈值、用客户类型的真实语料评价融合与文档多样性、补实际reranker对照，以及跨主机部署、备份恢复和更长时间的稳定性。它们都需要新证据，不能因为主流程已经跑通，就在简历或README里先写成完成。
