# NexusAgent-Eino 生产工程化设计

日期：2026-10-20。状态：用户已确认采用；本文是总体目标设计，实际实现与验证范围见首阶段验证报告。

## 1. 目标、来源与判断依据

用户要求在原 NexusAgent 完整产品范围内，推进 Go + Eino 的规模、可靠性和高性能改造，用于可以实际运行、演示和深入追问的后端项目。保留 Agent、RAG、Host/Expert、YAML 工作流、HITL、MCP、A2A、记忆及观测能力；不另换订单等行业场景。

基线来自 https://github.com/chengpeng-cp/nexus-agent ，提交 `5c7b81ee35492e35bca61881f061cafb3c65b363`。公开源码当前使用 Hertz 与自研执行循环；README 宣称的 Eino 尚未进入 go.mod 或生产调用链。已有产品内容能够支持 Eino；需要补齐的是执行语义、数据一致性、隔离与验证。

本次新仓库是 https://github.com/Epochex/NexusAgent-Eino 。保留上游历史和作者归属；新增提交明确标示本项目改造。当前审查为静态审查，未完成编译、集成测试或性能测量。

## 2. 方案选择

选择渐进替换：Hertz + Eino ADK/Graph + PostgreSQL + Redis Streams，沿用现有 Milvus、MinIO 和观测栈。维持模块化单体 server 与可扩展 worker；HTTP 生命周期不再承载长工作流的执行所有权。

比较过的另外两条路径：只把手写 ReAct 包成框架接口，改动小但不能解决恢复与一致性；直接拆分多个微服务并引入新调度系统，迁移面和运行成本大，现有需求不足以证明收益。因此不采用这两条路径。

Eino 主模块首先锁定 `v0.9.22`，以对应 tag 源码核对接口；eino-ext 的独立模块分别锁版并验证兼容，不引用浮动 main。常规模型消息路径满足本轮需求，不要求 Agentic Beta。Go 首先保持上游 `1.26.0` 下限，CI 与本地实际工具链版本必须记录。

## 3. 模块职责

| 模块 | 责任 | 边界 |
| --- | --- | --- |
| API/service | 用户归属、配置、发布、运行与审批接口、SSE 订阅 | 不在 handler 内持有长任务执行权 |
| Eino Agent runtime | ReAct、模型与工具调度、Host/Expert、事件转换 | 不代替授权、持久状态或工具幂等 |
| Workflow compiler | 已验证 YAML 转 Graph、分支、并行、子图、HITL | 发布时冻结 DSL、编译选项和依赖配置版本 |
| Execution service | Run/Step/Attempt、租约、取消、重试、审批恢复、结果对账 | PostgreSQL 是权威，队列只负责通知 |
| Tool service | Schema、允许列表、敏感操作审批、凭证、调用记录 | 模型输出不能扩大调用权限 |
| Knowledge/memory | ETL、版本索引、检索、记忆更新与隔离 | 向量库不成为用户归属或业务状态的权威 |
| Worker | 文档任务、执行任务、outbox 投递、回收与对账 | 有界消费与执行，等待审批不占执行槽 |
| Observability | OTel、Prometheus、结构化日志、压测和故障报告 | callback 不是持久业务日志；敏感内容默认脱敏 |

生产路径统一到一个 Eino Agent runtime，不长期维护两套 ReAct。`agent/naive` 保留教学用途。既有 `runtime.Runner` 是首个迁移接缝，前端事件名尽量兼容，新增运行标识与恢复信息采用明确字段。

## 4. 执行、状态与恢复

### 4.1 数据模型与不变量

- Run 绑定 owner、不可变定义版本、输入快照、运行参数、当前状态、状态版本、租约持有者与 fencing generation、截止时间和检查点引用。
- Step 以 `(run_id, execution_path)` 唯一标识一次逻辑节点；路径包含嵌套图位置和循环轮次，避免重复节点或未来循环覆盖结果。Attempt 记录每次实际尝试及调用结果。
- Run 状态包括 queued、running、waiting_approval、retry_wait、succeeded、failed、canceled、needs_attention。工具调用另外允许 unknown，不能把结果未知直接视为失败重试。
- 只有合法状态迁移可持久化；终态不可退回运行态。状态更新使用事务和版本比较，过期租约执行者不得继续提交结果。
- Run 创建、审批决定与后续任务通知通过事务 outbox 保持一致。消费者按逻辑任务 ID 去重，投递允许至少一次。

### 4.2 检查点

实现 PostgreSQL CheckPointStore。Run 保存 Eino 版本、图版本、状态 schema 版本和重新构造所需的运行选项；升级时不能拿新图直接恢复旧检查点。

明确区分正常中断存档、可控停机和强制退出。检查点保存成功才有对应恢复点；进程在任意指令退出不保证最后一个节点已经存档。恢复时核对工具调用账本，对已提交结果复用，对结果未知转入核对或人工处理。

### 4.3 审批

Approval 保存精确 interrupt ID/路径、待执行工具及参数摘要、参数 hash、发起用户、允许审批身份、过期时间与决定。恢复必须校验 owner、审批状态、版本和参数 hash。相同审批只能提交一个决定；并发重复提交返回已有决定，不重复投递有效恢复动作。

支持连续多次审批、多个并行分支审批以及子图审批；只恢复被批准的中断点。等待期间释放 worker 执行槽。工作流编辑产生新版本，不能改变已运行实例。

### 4.4 工具副作用

每次逻辑调用生成稳定 operation ID，重试保持不变；不同循环轮次或新操作不得复用。支持幂等键的远端直接传递；可查询结果的远端在超时后先核对；两者都不支持的写操作不自动重放，记录 unknown 并进入人工核对。不能宣称框架提供任意外部操作的 exactly-once。

## 5. Agent、权限与流式输出

以 Eino ADK ChatModelAgent/Runner 承接常规 Agent；现有模型网关通过适配器保留动态配置、fallback、usage 和错误分类。为工具绑定实现 Eino tools 适配器，调用入口重新验证所属用户、Agent 允许列表、参数 Schema 和审批条件。

统一处理整个请求的上下文预算：system、历史、长期记忆、RAG、工具定义及工具结果；保留 tool_call 与结果配对。记录实际迭代数与用量，设置总运行、模型调用、工具调用和输出大小上限。模型流开始输出后禁止无提示重放产生重复文本的 fallback。

区分浏览器断开订阅、用户主动停止生成、取消持久工作流、可恢复中断。浏览器断开不隐式取消持久工作流；交互式聊天断开按其明确运行策略停止并落终态。取消向模型和工具传递，处理不配合 ctx 的调用时仍有并发和时间边界。

事件包含 run_id、单调 seq、type、时间和数据版本。业务状态与可靠事件在数据库提交后对外可见。高频文本 delta 允许合并为有界批次，重连从已提交序号补发；允许客户端看到尚未提交的临时 delta 时，必须能用最终快照纠正。完成、失败、审批与取消不能被静默丢弃。

限制每个订阅缓冲和积压。慢订阅达到上限时关闭订阅并提示按 cursor 重连，不能拖死模型与 worker。事件历史有明确保留期、过期 cursor 错误与完整结果快照；token 级内容不进入高基数 Prometheus label。

## 6. RAG、MCP、A2A 与记忆

文档上传先持久化文档及 outbox。ETL 使用稳定文档版本、chunk 标识和 embedding 配置版本；任务部分失败可安全重放。索引状态经过 pending/building/ready/failed，只有完整 ready 版本可检索。更换 embedding 模型必须新建索引版本，禁止新查询向量与旧索引静默混用。

修复切分器递归不前进、格式解析不完整和静默丢页；解析警告对用户可见。保留稠密与关键词双路检索、RRF、可选 rerank，准确说明关键词实现，不将现有 ILIKE/TF-IDF 写成已具备 BM25 稀疏向量索引。检索失败必须区分降级和无相关结果，并通过固定评测集检验。

用户与 Agent 过滤在向量召回前生效，最终回表再次校验；长期记忆初始化、ADD/UPDATE/DELETE 与向量同步通过稳定记录 ID 和可恢复任务闭环。不能用数组下标对应模型重排后的事实操作。

MCP 贯通发现、Schema、持久注册、授权和 Agent 实际调用；重启重建工具注册表，限制调用超时、结果大小和并发。远程 HTTP 工具、MCP/A2A 目标落实 SSRF 与凭证边界。代码工具的隔离、网络、文件与资源限制单独验收，不能用 Docker 名称代替安全结论。

A2A 保留远程委派入口与客户端适配，明确能力声明；只有实现并验证的异步/streaming 功能才对外宣告支持。Host 路由与复杂任务拆分是不同能力，不为简单路由强制增加多专家并行。

## 7. 规模与性能策略

首先约束工作量，再优化热点：全局与用户级运行额度、模型提供方并发额度、工具并发额度、单运行分支上限、有界队列和请求体/输出大小限制。多 worker 下额度不能只是每个进程各自生效；使用可核对的共享租约额度，避免某个租户独占。

审批、退避和依赖等待不占执行槽；任务回收配合租约续期与 generation 校验。Redis 无消息时仍可从 PostgreSQL 找回待执行工作。DLQ 写失败不得 ACK 原任务，MaxRetry 与退避必须实际生效。

数据库按 owner、状态、时间和稳定游标分页建立索引；限定历史与事件回放窗口。图编译按不可变版本有界缓存；并行检索与工具调用受额度约束。模型客户端和数据库连接复用。批量写 chunk、向量和事件，但不得牺牲原子状态语义。依据 pprof/trace 和数据库计划优化，不能先填虚构 QPS 或性能提升百分比。

### 7.1 目标负载与测量定义

以下是验收目标，不是已达到的结果。参考配置为 server+worker 合计 4 vCPU/8 GiB，数据库、Redis、Milvus、MinIO 独立部署；报告必须写明所有机器、磁盘、网络、版本和配额，不能省略外置基础设施成本。

确定性外部服务桩：模型每次 250 ms、工具 100 ms；短运行包含两次模型和一次工具调用。第一档目标为 200 个 SSE 订阅、32 个可执行任务槽、每秒 10 个新运行，持续 30 分钟。按 50/200/500 订阅、8/32/64 槽及 1/5/10/20 个新运行每秒逐档测饱和点，超载必须明确拒绝或有界排队。

第一档平台控制接口（运行查询、审批提交、取消提交）p95 < 150 ms、p99 < 500 ms；有效负载内平台错误率 < 0.1%，没有静默丢失运行或终态、没有越权、没有可避免的重复写操作。等待模型的时长单列，不能扣掉数据库或队列延迟美化结果。SSE 空闲连接测试与活跃流量测试分别报告。

压测停止并排空后等待 5 分钟，重复三个周期；goroutine、连接、内存和积压不能持续随周期增长。使用开放到达率并报告 offered/completed/rejected/timeout/canceled/needs_attention、排队和执行分位数、首 token、CPU、堆、GC、锁和数据库连接。

真实模型另做受提供方配额与费用约束的端到端测试，报告实际模型、token、限流与任务正确率；不能把桩服务吞吐表述为真实 LLM 吞吐，也不能从本地 30 分钟测试推导线上年度可用性。

## 8. 验证与发布门槛

1. 单元/状态机：非法迁移、重复审批、过期版本、租约竞争、事件顺序、上下文与工具权限。
2. 真实基础设施集成：PostgreSQL 事务/CAS/outbox、Redis 重投与 ACK、索引和检查点持久化；mock 不能代替这些证据。
3. 进程/网络故障：执行中 kill worker、结果提交前退出、断开 Redis/数据库、模型限流、工具超时、慢 SSE 消费及重连。
4. 产品闭环：连续/并行/子图审批；审批后重启与版本变更；文档重复投递；多用户检索与记忆隔离；MCP 重启后实际调用；A2A 声明与行为一致。
5. 质量与性能：固定的至少 100 个知识查询，带相关 chunk 标注、无答案和权限反例；记录 Recall@k、排序、引用和答案正确性。检索链路消融与故障降级分别报告。完成前述开放负载和真实模型测试。

Go 检查覆盖 server/worker/cli 编译、go vet、相关单测、全包测试及支持平台上的 race；前端 typecheck/build。CI 不要求外部模型密钥；真实模型任务单独显式触发。数据库迁移先新增兼容字段与回填，再切流，最后移除旧路径；发布和回滚步骤可演练，不能在应用启动时偷偷做破坏性迁移。

每次报告注明上游基线、本项目提交、命令、环境、结果和限制。只有完成相应门槛才能称该模块经过生产工程验证；实际生产运行规模需要真实部署证据。

## 9. 分阶段交付

这是总体设计与阶段边界，各阶段另有可执行计划，不能用一份巨型计划同时重写所有子系统。

| 阶段 | 独立交付 | 退出条件 |
| --- | --- | --- |
| P0 基线 | 可构建环境、上游行为测试、风险记录、最小产品闭环 | 记录真实成功/失败，锁定兼容边界 |
| P1 Eino 执行内核 | 模型/工具适配、EinoRunner、事件桥、权限与取消、有界并发 | ReAct/Host/工具调用可回归；失败终态真实；已有页面可用 |
| P2 可靠工作流 | DSL→Graph、版本冻结、Run/Attempt、检查点、审批、outbox、worker 恢复 | 多次/并行/子图审批与故障恢复通过；未知副作用可核对 |
| P3 数据与集成 | 幂等 ETL、索引版本、RAG 评测、记忆一致性、MCP/A2A 闭环 | 重试、隔离、重启和检索质量有证据 |
| P4 规模与发布 | 共享配额、热点优化、负载与故障矩阵、部署回滚 | 达成或如实记录容量目标差距，交付可复现报告 |

顺序允许先修复阻塞基线或安全边界的局部问题，但不让未验证的旧执行器和新内核在生产路径长期分叉。每个阶段完成一个独立可测试、可提交、可演示的结果。
